as the single task board — do NOT create `.agents/tasks.md`.

**Done items do not stay on the board.** When an item closes, move it — with its date and closing
note, verbatim — to `tasks/done-archive.md`, the only other task file and the one that holds
nothing actionable. Anything live is in *this* file. Same convention as the partle and
kart-medulla repos. One exception: a **done step of a task that is still open** stays put — a
finished step loses its context once the decision it settled is filed away, so a cluster moves to
the archive whole, only once its last step closes.

- [ ] **Restarting kart-brain still costs about two minutes of battery data — the BLE link is not being closed cleanly** (added 2026-08-10, partially fixed the same day). `kb_bms` drops its Bluetooth connection to the pack without disconnecting. BlueZ keeps its own record of connected devices, so it is left claiming the pack is connected when nothing is, and while it believes that the pack is unreachable both ways: connect-by-address hits the stale entry, and scanning cannot find it either, because a BLE peripheral that thinks it holds a connection stops advertising. `_bluez_recover()` clears it, but only after three consecutive failures — hence the two-minute hole. Confirmed directly: `bluetoothctl info A5:C2:37:39:58:5D` reported `Connected: yes` at the same moment the node logged `Device with address ... was not found`.

  **Fixed so far.** `bace59f` — the systemd unit ran `bash -c 'source … && source … && ros2 launch …'`, a compound command, so bash forked the launch and stayed on as the service's main process. Non-interactive bash does not forward signals, so on stop bash took the SIGTERM and exited alone; systemd saw the main process gone, called the service stopped, and SIGKILLed the rest of the cgroup. The whole stop took one second for a stack containing a ZED camera and a TensorRT engine, which was the tell. **No node in this stack had ever run its shutdown code** — every `finally` and every rclpy shutdown hook was dead code on a restart. `exec` now makes ros2 launch the main process and `TimeoutStopSec` is 45s. Deployed to the Orin (`/etc/systemd/system/kart-brain.service`, `daemon-reload` done). `c447315` added SIGTERM handling and a bounded clean-disconnect path to `bms_node`, which the `exec` fix is what makes reachable at all.

  **NOT fixed — this is the open part.** With both commits deployed, a restart performed while the BLE link was live still left BlueZ at `Connected: yes` and the node still needed the three-strikes recovery (tested 11:54:20, node reconnected only after the usual two failures). So the disconnect is still not happening, or is happening and not clearing BlueZ's record.

  **Next step is instrumentation, not another guess.** The disconnect currently sits behind `except Exception: pass` in the BLE loop's `finally`, so a failure there is invisible. Log the outcome of `client.disconnect()` and log entry/exit of `shutdown()`, restart once with the link live, and the journal will say which of the two it is: shutdown never running, or disconnect running and failing.

  **Not a safety issue.** The battery data always comes back on its own; the cost is a blind dial for about two minutes after each restart.

- [x] **RESOLVED 2026-08-10, and it was never a transit bug — `ESP_HEALTH_STATUS` loses its last field in transit — the steering trip age never reaches the dashboard.** Found 2026-08-10 while answering "where is the reject counter". The firmware assembles seven int32 (`main/main.c`, `int32_t payload[7]` = `[flags, agc, heap_kb, i2c_errors, steer_frames, steer_rejects, steer_trip_age_s]`) and calls `KM_COMS_SendMsg(ESP_HEALTH_STATUS, payload, 7)`. `kb_coms_micro` splits `flags` off and forwards the rest, so `/esp32/health/data` should carry six. It carries **five**: observed `[0, 338, 0, 977300, 0]` and again `[0, 338, 0, 2354996, 0]`, i.e. `steer_trip_age_s` is absent and `protocol.decode_health_data`'s length guard leaves `health_steer_trip_age_s` unset.
  **This defeats the fix deployed the same day.** `20db00f` stopped `decode_health` dropping appended fields precisely so a stale latch could be told from a live one — the ambiguity that cost hours on 2026-08-08. The decoder is now correct and the field still never arrives, so the dashboard cannot show trip age at all.
  **Already ruled out:** the C++ handler does not truncate (`health_data_msg.payload.assign(frame_esp.payload.begin() + 1, frame_esp.payload.end())`, no cap); `SerialDriver::MAX_PAYLOAD` is 255; and neither side is a stale build — `kb_dashboard` and `kb_coms_micro` were rebuilt and the ESP32 flashed from `be82616` on 2026-08-10, and `steer_frames` climbs normally so the link is healthy. The loss is therefore between `KM_COMS_SendMsg` and the C++ handler: suspect the framing layer's LEN handling or the ESP32-side serialiser writing one element short. Next step is to dump a raw `ESP_HEALTH_STATUS` frame off `/dev/ttyACM0` and count the bytes — 7 int32 plus header should be 28 payload bytes.
  **Actual cause: the chip was flashed before the feature existed.** The raw dump settled it — `LEN=24`, i.e. the ESP32 was genuinely sending six int32, not seven, and nothing was being lost downstream. The firmware commit that adds `steer_trip_age_s` (`92a3248`, kart-medulla) is timestamped 10:58; the flash happened around 10:45. So the running image was `be82616`, whose `main.c` has `int32_t payload[6]` and `KM_COMS_SendMsg(..., 6)` — behaving exactly as written. The mistake was comparing a just-pulled working tree against a chip flashed thirteen minutes earlier and reading the difference as a protocol fault.
  Reflashed from current `dev`. `/esp32/health/data` now carries six fields ending in `-1`, the firmware's "no fault latched" value for trip age, so the chain from firmware to dashboard is complete.

With `wlP1p1s0` in `type AP` serving `kart`, `nmcli -f SSID,SIGNAL dev wifi list --rescan yes` returned exactly one row — `kart` itself, signal 0 — and no other network, in a room where `Robots_urjc` and phone hotspots are normally visible. A direct `sudo iw dev wlP1p1s0 scan` never returned at all: it was still running after 2 minutes and had to be killed by PID. (`pkill -f "iw dev wlP1p1s0 scan"` is the wrong way to kill it — the pattern matches the killing shell's own command line, so the shell kills itself and the SSH session dies with exit 255.) The AP kept serving `http://10.42.0.1/` with HTTP 200 throughout both attempts, so probing costs nothing, but it also tells us nothing. Consequence for the design below: every fallback attempt is blind and must drop the AP first to find out, so each attempt costs a real ~30 s window with no `kart` network. That is the argument against any repeating trigger — one attempt per discrete cable-unplug event, never a polling timer, or the kart loses its dashboard for 30 s out of every poll interval while parked somewhere with no known network.

**Option A — switch the single radio between AP and client mode on cable events. Free, and worth trying before spending anything.** Sequential mode-switching needs no new hardware and is what the Orin did before 2026-07-06, when it joined `Ruben's iPhone` at priority 100. Make it event-driven, never a blind timer: a NetworkManager dispatcher script on `enxfe9ca7a9ecdb` going **down** brings `kart-ap` down and lets the client profiles autoconnect on the priorities already set; if nothing associates within about 30 s it **must bring `kart-ap` back up**, because with neither AP nor client there is no dashboard at all and a bad guess at the track would leave the kart blind. On cable **up**, return to AP so the dashboard sits at a stable `10.42.0.1` whenever the tether is plugged. Two costs to accept: in client mode the `kart` network does not exist, so anyone on it is dropped and the dashboard address becomes whatever the joined network assigns (findable via Cloudflare or the hotspot's client list, but no longer fixed); and the obvious fallback network is the same phone that was meant to be plugged in, so this covers "cable unplugged or broken, phone in pocket" but not "phone absent".

**Option B — add a USB Wi-Fi dongle (~€10) as a second radio.** Strictly better behaviour, at the cost of money and a driver risk: built-in radio keeps beaconing `kart` continuously, dongle joins known networks as a client, no mode-switch state machine, no drop-outs, dashboard address never moves. Pick a chipset with in-tree support for JetPack 6 (kernel 5.15, aarch64) — driver availability is what bites on Jetson, so do not buy on price alone.

**How to test whichever option is built — three cases, and the third is the one that matters.** The test severs the tester's own remote access, because `ssh orin-remote` and `kart.rubenayla.xyz` both ride the Cloudflare tunnel over the tether being unplugged. So instrument first and read the record afterwards rather than trying to watch live: `nohup` a script that appends `nmcli -t -f DEVICE,TYPE,STATE,CONNECTION device`, `nmcli -t -f CONNECTIVITY general`, `iw dev wlP1p1s0 info` and `ip route | grep default` to a log file every 5 s, then pull the cable. Keep a laptop or phone joined to the `kart` Wi-Fi (pwd `umotorsport`) as the local way back in at `ssh orin-local` / `http://10.42.0.1/`, and note `tcpdump` is **not** installed on the Orin if packet-level detail is ever needed. Cases: (1) **known network in range** — unplug with a phone hotspot on and reachable; pass = a client profile associates within ~30 s, the hotspot shows a connected device, `ip route` regains a default via Wi-Fi, and the dashboard answers on the address that network assigned. (2) **cable back** — replug; pass = the default route returns to the tether (metric 100 beats Wi-Fi's 600) and the `kart` AP is back up, so `http://10.42.0.1/` works again. (3) **no known network in range** — unplug with every known hotspot off or out of range; **pass = `kart-ap` comes back up within ~30 s and the dashboard is reachable at `10.42.0.1` again.** Case 3 is the whole safety argument for the design and the easiest to skip, since cases 1 and 2 both look fine while it is broken; a mode-switch that strands the kart with no AP and no client is worse than having no fallback at all. Verify each from the log plus a real dashboard load, not from `nmcli` alone.

Either way the desired priority order — USB tether first, then the phone hotspots, then `Robots_urjc` — needs no new config: the tether's DHCP default route already has **metric 100 against Wi-Fi's 600**, so USB wins automatically whenever it is plugged, and the Wi-Fi profile priorities above already encode the rest. Keep `kart-ap` as the resting state with autoconnect priority above every client profile, so a reboot at the track always comes up with `kart` present.
